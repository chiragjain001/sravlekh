# Load test results — 2026-09-11

**First executed load test in this repository.** `load-tests/README.md` previously
said "Status: written, never executed", and both audits carried
"Load testing — **C** — 5 k6 scripts exist; **never executed**" as an open item.

Read the environment caveat in §4 before quoting any number from this file.

---

## 1. What was run, and what was not

| Script | Status | Why |
| :--- | :--- | :--- |
| `read-path-baseline.js` (new) | **EXECUTED** | Needs only what `packages/db/src/seed.ts` creates |
| `grading-burst.js` | **NOT RUN** | Needs an `ANSWER_SHEET_ID` on an ONGOING/EVALUATING exam |
| `ai-evaluation-burst.js` | **NOT RUN** | Needs `DELIVERY_IDS` with subjective Responses already submitted |
| `blueprint-generation-burst.js` | **NOT RUN** | Needs a live AI provider key; would bill real money |
| `report-generation-burst.js` | **NOT RUN** | Needs seeded exams with graded results |
| `document-processing-burst.js` | **NOT RUN** | Needs seeded document bundles and page images |

The five domain scripts need state a fresh database does not have. Running them
without it produces 404s at speed, which measures nothing — so they remain
honestly unexecuted rather than run to produce a green-looking result. Closing
that gap means a load-test fixture seeder, which is its own piece of work.

`read-path-baseline.js` was written for this run because it exercises the path
every screen depends on — JWT verification, tenant scoping, a Prisma read — using
only data the existing seed provides.

## 2. Rate limiting — verified working under load

The **first** run failed 90.56% of requests. Investigated rather than assumed:
every failure was `429 RATE_LIMITED`. The throttler was doing its job.

That is a real verification. At ~145 req/s from a single authenticated identity,
the global throttle (10/s, 100/min) rejected the excess cleanly, with a
structured error body and no 5xx.

Note the tracking strategy, which is correct and worth stating because the
obvious implementation would be wrong: `UserThrottlerGuard` keys authenticated
routes by **user id**, falling back to IP only for public routes. A whole
institute behind one NAT gateway therefore does **not** share a single budget.

Capacity numbers below were taken with the limits raised
(`THROTTLE_SHORT_LIMIT` / `THROTTLE_MEDIUM_LIMIT`, made configurable for exactly
this reason — see §5).

## 3. Measured capacity

`read-path-baseline.js`, 20s per level, 4 requests per iteration
(`/auth/me`, `/questions`, `/batches`, `/students`).

| VUs | Throughput | Median | p95 | Errors |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 44 req/s | 21 ms | 37 ms | 0% |
| 5 | 122 req/s | 39 ms | 66 ms | 0% |
| 10 | 135 req/s | 70 ms | 119 ms | 0% |
| 20 | 123 req/s | 153 ms | 272 ms | 0% |
| 40 | 175 req/s | 219 ms | 412 ms | 0% |

**Saturation begins between 5 and 10 concurrent users.** Throughput plateaus
around 120–175 req/s while latency grows roughly linearly with concurrency —
the classic signature of a saturated resource, where added load only queues.

**Zero errors at every level**, including 40 VUs. No connection exhaustion, no
timeouts, no 5xx. The system degrades by getting slower, not by failing, which is
the correct shape.

Against `11-PERFORMANCE-REQUIREMENTS.md`'s p95 < 300 ms for reads: **met up to
~20 concurrent users on this hardware, crossed at 40** (412 ms).

## 4. Environment — read this before quoting the numbers above

These were measured on a **developer laptop under heavy memory pressure**, not
production-like hardware:

- 5.9 GB total RAM with **~0.7 GB free**; Docker Desktop had already crashed once
  during this session from memory exhaustion;
- Postgres 16 in Docker on the same host as the API;
- the developer's own `next dev` and `nest start --watch` processes running
  concurrently;
- the API run with `node --enable-source-maps`, which adds real overhead;
- k6 itself competing for the same CPUs.

**The absolute throughput ceiling is a property of this laptop, not of the
application.** What transfers is the *shape*: the plateau, the linear latency
growth past saturation, and the zero error rate.

**The bottleneck is not the database connection pool.** During the 40-VU run
Postgres reported **10 of 100** connections in use, against a Prisma default pool
of 17 (8 CPUs × 2 + 1). Pool exhaustion was the first hypothesis and the
measurement ruled it out.

## 5. Findings

1. **Connection pool size is never configured.** Prisma's default is
   `num_cpus × 2 + 1` — derived from the *container's* CPU count, which is not
   something anyone has reasoned about here. With 5 API replicas at 17 each that
   is 85 connections against Postgres's default `max_connections=100`, and the
   sixth replica starts failing to connect. Not a problem today (single process,
   10 connections), and a real one at the first horizontal scale-out. It should
   be set explicitly via `?connection_limit=` on `DATABASE_URL`.
2. **Throttle limits were hardcoded.** They could not be tuned in production
   without a redeploy, and no load test could get past them to measure anything.
   Now `THROTTLE_SHORT_LIMIT` / `THROTTLE_SHORT_TTL_MS` /
   `THROTTLE_MEDIUM_LIMIT` / `THROTTLE_MEDIUM_TTL_MS`, defaulting to the previous
   values so behaviour is unchanged.
3. **`/auth/me` is not free.** At 131 ms average it is the cheapest authenticated
   request in the system and still does a database lookup per call. Every screen
   calls it. A short cache keyed on the JWT's `sub` + `tokenVersion` would remove
   it from the hot path — but only after measuring on real hardware, since the
   figure above is dominated by this environment.

## 6. Reproducing

```bash
docker compose -f infra/staging/docker-compose.yml up -d staging-db
cd packages/db && DATABASE_URL=... npx prisma migrate deploy && npx tsx src/seed.ts

# API against the staging DB, throttle raised so the app is what is measured
DATABASE_URL=... REDIS_URL=... JWT_SECRET=... GOOGLE_CLIENT_ID=... \
  ENABLE_DEV_LOGIN=true PORT=4444 RUN_WORKERS=false \
  THROTTLE_SHORT_LIMIT=100000 THROTTLE_MEDIUM_LIMIT=1000000 \
  node apps/api/dist/main.js

TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"role":"TEACHER"}' localhost:4444/api/v1/auth/dev-login | jq -r .accessToken)

BASE_URL=http://localhost:4444/api/v1 AUTH_TOKEN=$TOKEN \
  INSTITUTE_ID=demo-institute-1 VUS=20 DURATION=30s \
  k6 run load-tests/read-path-baseline.js
```

k6 v0.54.0. The Windows MSI needs elevation; the standalone binary from the
GitHub release does not and is what was used here.
