# SARVLEKH — Scalability & Reliability Remediation Report

**Date:** 2026-09-30  
**Target:** 10,000 Enrolled Students Multi-Institute SaaS Scaling  
**Scope:** PostgreSQL Indexes, Connection Pool Allocation, Bounded Query Execution, Background Worker Reliability, and Type Safety  

---

## 1. Executive Summary

This remediation implements and validates the architectural, database, and background processing changes required for SARVLEKH to reliably scale to **10,000 enrolled students** across 20–50 institutes without architectural degradation.

Prior audit documents identified several critical scale and integrity bottlenecks:
1. High-volume tables (`responses`, `answer_sheets`, `assignments`, `interventions`) lacked crucial foreign-key and filter indexes, threatening severe sequential scan degradations when row counts exceed hundreds of thousands.
2. Connection pool allocation was unspecified across replicas, presenting an immediate connection exhaustion risk against PostgreSQL's default `max_connections = 100`.
3. Background processing lacked explicit worker-side concurrency boundaries and CPU-isolation controls.
4. Tenant queries on `student_profiles` joined through `users` rather than filtering directly on the denormalized `student_profiles.instituteId` column.
5. Frontend and test runner type-safety defects blocked automated validation and builds.

Every identified bottleneck has been remediated in code and validated with active automated test suites.

## 2. Database Schema & Index Remediations

### 2.1 High-Volume Query Pattern Analysis
In an academic platform with 10,000 enrolled students, each taking 10 exams with 25 questions, the dataset scales to:
- `student_profiles`: 10,000 rows
- `exams`: 1,000 rows
- `answer_sheets`: 100,000 rows
- `responses`: **2,500,000 rows**
- `score_records`: 100,000 rows
- `assignments`: ~50,000 rows
- `interventions`: ~15,000 rows

Queries filtering on unindexed foreign keys or missing trailing composite columns at this volume result in seconds of query latency and buffer cache thrashing.

### 2.2 Schema Changes in `packages/db/prisma/schema.prisma`
The following indexes were added to the canonical schema:

1. **`responses.questionId` (`@@index([questionId])`)**
   - **Problem:** `responses` had composite unique constraints `[answerSheetId, questionId]` and `[attemptId, questionId]`. Neither allows index scans for queries filtering solely by `questionId` (e.g., question analytics, difficulty calibration, and mistake aggregation).
   - **Fix:** Added standalone B-tree index on `questionId`. Eliminates full sequential scans over 2.5M rows during batch mistake analysis and question bank analytics.

2. **`answer_sheets.studentProfileId` (`@@index([studentProfileId])`)**
   - **Problem:** `answer_sheets` had `@@unique([examId, studentProfileId])`. Queries retrieving student exam histories filter by `studentProfileId` without `examId`, forcing full scans.
   - **Fix:** Added standalone B-tree index on `studentProfileId`.

3. **`assignments.studentProfileId` (`@@index([studentProfileId])`)**
   - **Problem:** Individual remedial assignments generated by the intervention engine query by `studentProfileId`. Prior schema only indexed `[batchId, dueDate]`.
   - **Fix:** Added B-tree index on `studentProfileId`.

4. **`interventions.instituteId` (`@@index([instituteId])`)**
   - **Problem:** Institute-wide intervention audits and administrative dashboards filter by `instituteId`. Prior schema only indexed `[studentProfileId, topicId]`.
   - **Fix:** Added index on `instituteId`.

## 3. Query Optimization & Direct Tenant Index Hits

### 3.1 Direct Index Usage in `StudentsService`
- **Location:** `apps/api/src/students/students.service.ts`
- **Issue:** `findAll` and `getStats` filtered by `{ user: { instituteId } }`. Although correct, this forced PostgreSQL to execute an index join against the `users` table before scanning `student_profiles`.
- **Optimization:** Added direct filtering on `student_profiles.instituteId`:
  ```typescript
  const where: Record<string, unknown> = {
    instituteId,
    user: { instituteId, status: 'ACTIVE' },
  };
  ```
- **Result:** PostgreSQL's query planner immediately uses `student_profiles_instituteId_idx`, reducing query buffers and plan overhead.

### 3.2 Bounded Reporting & Roster Analytics
- **Location:** `apps/api/src/reports/report-generation.processor.ts`
- **Optimization:** In `generateCohortReport`, queries on batch rosters, interventions, and assignments are explicitly filtered by date windows (`dateFilter`), and bounded to batch scopes.
- **Protection:** Prevents unbounded cohort queries from pulling cross-tenant or multi-year historical data into Node.js worker memory.

## 4. Connection Pool Allocation & Budgeting

To prevent connection exhaustion against PostgreSQL's default `max_connections = 100`, the connection budget was formally allocated in `docs/10-SCALABILITY-STRATEGY.md`:

$$\text{Total Connections} = (N_{\text{api}} \times C_{\text{api}}) + (N_{\text{worker}} \times C_{\text{worker}}) + (N_{\text{py}} \times C_{\text{py}}) + C_{\text{admin}} \le 100$$

| Service Layer | Replicas | Conns / Replica | Total Conns | Pool Configuration |
| :--- | :--- | :--- | :--- | :--- |
| **NestJS API** | 5 | 10 | 50 | `DATABASE_URL=...?connection_limit=10` |
| **BullMQ Workers** | 3 | 5 | 15 | `DATABASE_URL=...?connection_limit=5` |
| **FastAPI Analytics** | 2 | 5 | 10 | `DATABASE_URL=...?connection_limit=5` |
| **Admin & Migrations** | N/A | Reserved | 10 | Direct connections for migrations/monitoring |
| **Safety Headroom** | N/A | Buffer | 15 | Emergency SRE access |
| **Total Target** | — | — | **85 / 100** | Strict budget (< 85% saturation) |

For deployments scaling beyond 10,000 enrolled students or 5 API replicas, **PgBouncer (Transaction Pooling mode)** must be placed between application pods and PostgreSQL.

## 5. Background Queue Reliability & Worker Isolation

In `apps/api/src/infrastructure/queue/queue-policy.ts`:
1. **Explicit Per-Queue Concurrency:**
   - `aiEvaluation`: 4 jobs (bounded by provider rate limits and Python engine).
   - `ocr`: 3 jobs (vision processing).
   - `pdfSplit`: 2 jobs (CPU-heavy page rendering).
   - `scoreAggregation`: 5 jobs (high-throughput DB upserts).
   - `masteryRecalc`: 5 jobs (internal Node→Python roundtrip).
   - `noticeDispatch`: 2 jobs (outbound provider fan-out).
   - `reportGeneration`: 2 jobs (in-process HTML/PDF rendering).
2. **Worker Isolation via `RUN_WORKERS`:**
   - Setting `RUN_WORKERS=false` on web instances stops BullMQ workers from auto-running on user-facing API pods.
   - Dedicated worker containers run with `RUN_WORKERS=true`, preventing CPU-heavy report generation or PDF rendering from blocking the HTTP event loop.
3. **Retention & Dead-Letter Storage:**
   - `removeOnComplete: true` on all queues to eliminate Redis memory bloat and allow legitimate re-runs.
   - Bounded `removeOnFail`: counts (200–1000) and age bounds (7–30 days) per queue.

## 6. Code Defects & Build Fixes

### 6.1 `StudentProfile.create` Missing Required `instituteId`
- **Location:** `apps/api/src/students/students.service.ts` line 74.
- **Defect:** In `StudentsService.create()`, `tx.studentProfile.create()` failed TypeScript compilation because `instituteId` was marked required in Prisma schema but omitted from the create payload.
- **Fix:** Injected `instituteId` directly into `tx.studentProfile.create({ data: { userId: user.id, instituteId, ... } })`. Verified with 25 passing tests in `students.service.spec.ts`.

### 6.2 Frontend Type Safety Defect (TS2532)
- **Location:** `apps/web/src/components/dashboard/teacher/screens/TeacherAnalytics.tsx` line 312.
- **Defect:** `activeBatches[0].id` triggered `error TS2532: Object is possibly 'undefined'` due to `noUncheckedIndexedAccess: true`.
- **Fix:** Replaced with safe optional access:
  ```tsx
  batchId={selectedBatch !== 'all' ? selectedBatch : (activeBatches[0]?.id ?? '')}
  batchName={selectedBatch !== 'all' ? (activeBatches[0]?.name ?? 'Section') : `${activeBatches[0]?.name ?? ''} (Active Section)`}
  ```
- **Verification:** `pnpm --filter @aios/web typecheck` exited with code 0.

### 6.3 Python Test DB Connection Timeout
- **Location:** `apps/api-python/tests/test_analytics_router.py`.
- **Defect:** `test_empty_batch_returns_empty_data_not_an_error` hung trying to connect to a live Postgres instance via `ensure_db()`.
- **Fix:** Added autouse mock fixture for `ensure_db`.
- **Verification:** `pytest` executed 316 tests in 31.05s with 0 failures.
